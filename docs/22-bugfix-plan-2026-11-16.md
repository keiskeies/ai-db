## P1（高）driverFor 并发建池泄漏 + 连接删除竞态【独立】

### 现象与根因
- `apps/gateway/src/manager.ts:117-130` 的 `driverFor()`：同一 `connectionId` 首次被并发请求（典型触发：打开库树的同时发 SQL）时，两个请求都 miss 缓存、各自 `await createDriver()`（各自建池 + 可能建 SSH 隧道），随后 `clients.set` 后到者覆盖先到者——先建的 driver 永不 close，连接池与隧道长期泄漏。
- 与 `close()` 的竞态：`close(connectionId)` 之后（连接已删除，routes.ts:421 先 `manager.close` 再删记录），若某处正在 `await createDriver`，创建完成后仍会 `clients.set` 把已删除连接的 driver 塞回 map 常驻。
- 全仓库无 per-connection in-flight 去重。

### 改造
在 `ConnectionManager` 内：

```ts
private inFlight = new Map<string, Promise<CachedDriver>>();
private closedFlags = new Map<string, boolean>();

private driverFor(connectionId: string): Promise<Driver> {
  const cached = this.clients.get(connectionId);
  if (cached) { this.store.touchConnection(connectionId); return Promise.resolve(cached.driver); }

  const pending = this.inFlight.get(connectionId);
  if (pending) return pending.then((bundle) => {
    if (this.closedFlags.get(connectionId)) throw new DbError('连接不存在', { code: 'CONNECTION_NOT_FOUND', status: 404 });
    this.store.touchConnection(connectionId);
    return bundle.driver;
  });

  const created = this.createDriverCached(connectionId);
  this.inFlight.set(connectionId, created);
  return created;
}

private async createDriverCached(connectionId: string): Promise<CachedDriver> {
  try {
    const conn = this.store.getConnection(connectionId);
    if (!conn) throw new DbError('连接不存在', { code: 'CONNECTION_NOT_FOUND', status: 404 });
    const secret = this.store.getConnectionSecret(connectionId);
    const bundle = await createDriver(conn, secret);
    if (this.closedFlags.get(connectionId)) {
      await bundle.close().catch(() => undefined);   // 创建期间连接已被删除：立即关掉，绝不进缓存
      throw new DbError('连接不存在', { code: 'CONNECTION_NOT_FOUND', status: 404 });
    }
    this.clients.set(connectionId, bundle);
    this.store.touchConnection(connectionId);
    return bundle;
  } finally {
    this.inFlight.delete(connectionId);
  }
}
```

`close(connectionId)`（现 manager.ts:1266-1279）开头补 `this.closedFlags.set(connectionId, true);`。

连接重新创建时清除标志：`createConnection`/`updateConnection` 成功后若复用相同 id（当前 id 为 randomUUID，仅 updateConnection 会复用），执行 `this.closedFlags.delete(connectionId)`。若确认无 id 复用，在注释中说明即可。

`closeAll()`（1281-1284）清理时：把 `clients` 全部 close 后 `closedFlags.clear()`；`inFlight` 中 pending 创建完成会走「已关闭即关」分支，无需额外处理。

### 验收
1. 单测：`driverFor` 并发调用同一 connectionId 10 次，断言 `createDriver` 只被调用 1 次、最终 `clients` 里只有 1 个 driver。
2. 单测：`createDriver` 进行中调用 `close(connectionId)`，断言创建完成的 driver 被立即 close、不进入 `clients`。
3. 现有事务/连接相关测试全绿（`apps/gateway/src/manager.test.ts` 或同目录 `*.test.ts`；改动后跑 `apps/gateway` 全部单测）。

## P2（高）Agent turn 失效竞态：stop/断开后回合仍执行并覆盖终态【串行】

### 现象与根因
`apps/gateway/src/routes.ts:2485-2493`：SSE `res.on('close')` 触发 `host.abort(sessionId, 'disconnected')`；`apps/gateway/src/agentHost.ts:310-324` 的 `abort()` 只会全量清 pending approvals + 置 store 状态，**不会**中止在途 provider 流（`startTurn` 里 `runtime.run({...signal})` 用的 signal 是 `startTurn` 内部新建的 controller，abort 从未触发它）。代码自证（agentHost.ts:370/406-407/626）：

- 用户点停止（`POST /abort` → `abort('user')`）后，provider 流继续跑，工具继续执行；turn 结束时 `startTurn` 照常写 assistant 消息、summary、`resume`、tokens——把用户已经停掉的回合状态覆盖成"完成"。
- abort 时全部 pending approvals 被 `resolve('deny')`（agentHost.ts:317-322），此后回合内任何等待审批的 tool 都会以 deny 失败继续，但回合不自知已失效，最终以 `status: 'aborted'` 收尾后**仍会写检查点/更新 summary/turns**（agentHost.ts:650-710），与「用户已停止」的事实矛盾。

### 改造（最小、低风险方案）
在 `AgentHost` 内增加失效标记，让被 abort 的回合收敛：

1. 新增 `private turnInvalidated = new Map<string, boolean>();`
2. `abort(sessionId, cause)`（310-324）内、`controller.abort()` 后：`this.turnInvalidated.set(sessionId, true);`
3. `startTurn` 中：
   - `runtime.run` 返回后（626-644），检查 `const invalidated = this.turnInvalidated.get(sessionId) === true;`
   - 若 `invalidated`：
     - **跳过** store.appendMessage 的 assistant 消息与 resume 检查点（650-689 段整体跳过）；
     - `updateSession`（693-710）仅保留 `status: 'aborted'`、`resume: null`，不叠加 summary/tokens/turns/steps（保持上一回合计数不变）。
   - 若 `status === 'error'` 且 `invalidated`，保持 `status: 'aborted'`（不把 `error` 覆盖 aborted 的语义）。
4. finally（719-730）中：`this.turnInvalidated.delete(sessionId);`
5. 双回合并行防护：`startTurn` 开头（370-371）新增：`if (this.turnInvalidated.has(sessionId)) throw new DbError('该会话正在结束，请稍后再试', { code: 'SESSION_BUSY', status: 409 });`——abort 后立刻再发新回合会被拒绝，直到旧回合 finally 清掉标记（provider 卡死时由 stall 看门狗兜底让 runtime.run 返回）。

不改 SSE 路由、不改 runtime.ts、不改 `abortCauses` 语义（`disconnected` 路径仍由 abort() 记录、`unfinished` 判定仍按现状，只有「invalidated 且 disconnected」的情况才不写检查点——用户没主动点停止但连接断开，检查点保留，这是现状语义，保持不变）。

### 验收
1. 单测（`apps/gateway/src/agentHost.test.ts` 或新建）：mock runtime.run 为一个「abort 后仍 resolve」的 promise；断言：abort 后回合不写 assistant 消息、不覆盖 summary、resume 置 null、turns 不递增；abort 后立即 `startTurn` 同一 sessionId 抛 `SESSION_BUSY`。
2. 现有 abort/approval/resume 相关单测全绿（`packages/core/src/agent/runtime.test.ts`、agentHost 相关）。
3. 手工/e2e：跑一个发 SQL 的回合，点停止，确认状态停留 aborted、无「继续」按钮；随后新回合正常。

## P3（中）SSE 心跳不重置 idle 定时器 → 90s 静默合法回合被误杀【独立】

### 现象与根因
`apps/desktop/src/lib/api.ts`：`readWithIdleCeiling`（185-227）的 90s 定时器（182：`TURN_IDLE_CEILING_MS = 90_000`）在每次 `reader.read()` 挂起期间持续倒计时；服务端只有 15s 心跳（routes.ts:2482-2484），且心跳与 `data:` 帧**都**会让 `reader.read()` resolve → 定时器重置。真正的问题：**agent 回合在 provider 返回前（一次模型 stream 可能静默数分钟，长思考/长工具执行）服务端不发任何字节**，此时客户端 90s 定时器照跑 → `reader.cancel()` + `TURN_CHANNEL_IDLE`，把合法进度误杀，且 `reader.cancel()` 触发网关 `res.on('close')` → 回合被 abort('disconnected')。

### 改造（双端配合）
- **服务端（routes.ts 2482-2484）**：心跳间隔保持 15s，但新增「无事件静默」保活：当回合处于 provider 等待期间（无字节可发），heartbeat 无法覆盖——因此服务端不做改动，由客户端放宽。
- **客户端（api.ts）**：
  - 把 `readWithIdleCeiling` 的字节级上限从 90s 提高到与 `PROVIDER_STALL_MS`（packages/core/src/agent/providers/common.ts，`PROVIDER_STALL_MS=300s`）对齐的 **10 分钟（600_000ms）**，作为「半开连接」兜底；
  - 新增**事件级**静默上限：在 `streamTurn` 循环维护 `lastActivityAt（配 ref/闭包变量）`：对**任何**帧（含 `: ping` 心跳、`data:` 事件）都更新时间；在下一次进入 `reader.read()` 前，若 `Date.now() - lastActivityAt > EVENT_IDLE_MS（建议 300_000ms = 5 分钟）` 则主动 cancel + 抛 `TURN_CHANNEL_IDLE`——要求服务端在 5 分钟内至少有一次心跳或事件（15s 心跳满足）。这样「模型静默 <5min」不误杀，「连接半开 >10min 无字节」仍兜底。
  - 保留现有 `signal` abort 语义（用户停止仍原样抛 AbortError）。

### 验收
1. 单测（api.ts 已导出 `readWithIdleCeiling` 供测试，见 api.ts:184 注释）：构造「60s 一次 `: ping`、无 data 帧」流 → 字节级 10min 不触发、事件级 5min 不触发；构造「完全无字节 10min」→ 字节级触发。
2. 手工/e2e：慢 SQL（几秒无事件）不再被 90s 误杀。

## P4（高）mssql 事务提交/回滚失败时池连接泄漏【独立】

### 现象与根因
`apps/gateway/src/drivers/sqlserver.ts:256-266` `finishTransaction`：
- 先 `txTransactions.delete(sessionId)` 再 `try { commit/rollback } catch { throw }`，**无 finally**。
- mssql `Transaction` 独占一条池连接（`beginTransaction` 里 `new Transaction(pool)`，225-231）；commit 抛错时事务仍开、连接既不回滚也不归还池，且 `txTransactions` 已删——**没有任何路径能再触达这条连接**，池 max=3 直接耗尽。
- `beginTransaction`（228-229）`transaction.begin()` 抛错时 transaction 未入 map，但连接已被 Transaction 持有且无人归还——**同样泄漏**。
- 连带：`manager.txSessions` 条目在 commit/rollback 失败后残留到 15 分钟 reaper，reaper 的 `rollbackTransaction` 又因 `txTransactions.delete` 已删而抛 TX_NOT_FOUND 被吞（manager.ts:1026-1028）——双残留。

### 改造
```ts
private async finishTransaction(sessionId: string, commit: boolean): Promise<void> {
  const transaction = this.txTransactions.get(sessionId);
  if (!transaction) throw new DbError('事务会话不存在或已结束', { code: 'TX_NOT_FOUND', status: 404 });
  try {
    if (commit) await transaction.commit();
    else await transaction.rollback();
  } catch (err: any) {
    // 提交/回滚失败后事务对象仍持有池连接：撤销而不是放走，避免池被无主事务占死。
    await transaction.rollback().catch(() => undefined);
    throw new DbError(err?.message ?? `${commit ? '提交' : '回滚'}事务失败`, { code: commit ? 'TX_COMMIT' : 'TX_ROLLBACK' });
  } finally {
    this.txTransactions.delete(sessionId);
  }
}
```
`beginTransaction`：
```ts
const transaction = new mssql.Transaction(pool);
try {
  await transaction.begin();
} catch (err: any) {
  await transaction.rollback().catch(() => undefined);
  throw new DbError(err?.message ?? '开启事务失败', { code: err?.code ?? 'MSSQL_TX_BEGIN' });
}
this.txTransactions.set(sessionId, transaction);
```
（若 `rollback()` 在未成功 begin 时抛错，换成 `transaction.cancel?.()` 或注释说明依赖真实环境验证 mssql 对未提交事务的释放语义。）

### 验收
1. mssql 环境：begin → 语句成功 → 使 commit 失败（破坏事务状态）→ 断言池仍可用（`pool.size` 回到上限）、`txTransactions` 无残留、manager.txSessions 被 reaper 清掉。
2. 无环境 CI：`npm run typecheck` + `apps/gateway` 单测全绿；代码注释注明「待真实 mssql 验证事务对象释放语义」。

## P10（中）mobile 审批并发丢弹窗【独立】

### 现象与根因
`apps/mobile/App.tsx:910-926`：`approval_required` 直接 `setApproval(...)`、`approval_resolved` 直接 `setApproval(undefined)`——无 FIFO 队列；一次回合内并发到达多条审批（如批量建表）只显示最后一条；点「仅此一次」resolve 后 `setApproval(undefined)` 把其他 pending 一并清掉。桌面端有 `apps/desktop/src/lib/approvalQueue.ts`（FIFO + 按 approvalId 出队），移动端没有。

### 改造
在 `App.tsx` 内实现与桌面等价的最小队列：
- `const [approvalQueue, setApprovalQueue] = useState<ApprovalState[]>([])`；`approval` 改为派生：`const approval = approvalQueue[0]`。
- `approval_required`（910-920）：`setApprovalQueue(q => q.some(i => i.approvalId === event.approvalId) ? q : [...q, {...}] )`。
- `approval_resolved`（922-926）：`setApprovalQueue(q => q.filter(i => i.approvalId !== event.approvalId))`。
- 用户点「允许/拒绝」的 resolve 回调：成功后按 approvalId 从队列移除；失败（404 已过期）也移除。
- 回合的 `setApproval(undefined)` 收尾（907/1199/1233）→ `setApprovalQueue([])`。

### 验收
1. 手工（移动端，`npm run build:mobile` export:web 后真机/浏览器）：回合连发 3 个审批，断言依次弹出、resolve 一条后下一条出现。
2. typecheck 通过。

## P11（低）QueryView 编辑器卸载丢失未提交 SQL【独立】

### 现象与根因
`apps/desktop/src/components/QueryView.tsx:231`（`updateTab` 依赖 `[tab.id, updateTab]`）及 `sqlRef`（160-229 的 EditorView 生命周期）：卸载时 `sqlRef.current` 是旧快照，`view.state.doc` 才是最终文本；卸载 effect 未必把最新 doc 存回 tab。

### 改造
- 在 EditorView 卸载分支（destroy 前）补：`sqlRef.current = view.state.doc.toString(); updateTab(tab.id, { sql: sqlRef.current });`——注意避免 updateTab 本身触发卸载的循环，用 ref 判重（卸载时若已是同一 sql 则跳过）。
- 或：把「保存 SQL 回 tab」移入独立 `useEffect(() => () => { const v = viewRef.current; if (v) updateTab(tab.id, { sql: v.state.doc.toString() }); }, [])`，卸载时读取最新 doc。

### 验收
1. 手工：输入未提交 SQL → 切换 tab → 切回，断言 SQL 保留。
2. typecheck + desktop 单测全绿。

## P12（低）DataGrid 行号 key 的约束【记录型修复】

### 现象与根因
`apps/desktop/src/components/DataGrid.tsx:179-188`：`<tr key={rowIndex}>`，`rowIndex = visibleStart + offset`——编辑/删除行后行号偏移，`onCellEdit(rowIndex)` 回调用的是偏移后的新行号，可能落到错误行（尤其 virtualized 窗口 + 排序/过滤）。

### 改造
本组件语义即以行号为 key（表格行即数据行，无稳定主键）；采用「记录约束 + 调用方重置窗口」：
- 在 DataGrid 定义上方注释说明：数据更新后（增删行/排序/过滤）调用方必须重置可见窗口（`resetScroll/useEffect 依赖数据长度`），否则行号偏移会导致编辑/选择串位。
- 检查调用方（表数据浏览器等）在数据替换后是否已重置窗口；未重置的在调用方补一次窗口重置。

### 验收
1. 调用方数据替换后窗口重置：手工删除一行后立即编辑原下一行，断言编辑落在正确行。
2. typecheck 全绿。

## P14（低）SSH 隧道 listen 失败泄漏 / MCP execFile 进程残留【独立】

### 现象与根因
- `apps/gateway/src/drivers/ssh.ts:65-73`：`server.listen` 失败路径只 `client.end()`，不 `server.close()`（server 已创建未 listen，Windows 下句柄泄漏）；`close()`（79-84）在有活跃 socket 且 destroy 失败时可能挂起。
- `apps/gateway/src/builtinMcp.ts:545-557`（runCommand）与 `1048-`（runProcess）：`execFile` 的 `timeout` 在 Node≥20 已弃用，超时后子进程若未响应 kill 可能残留。

### 改造
- ssh.ts：listen 失败分支补 `server.close()`（回调内 resolve）；`close()` 用 `Promise.race([server.close 回调, 2s 超时])` 兜底防挂起。
- builtinMcp.ts：`runCommand/runProcess` 迁移到自己的 `execFile` 包装：超时后 `child.kill()`（Windows 用 `taskkill /pid /T /F` 或 `process.kill(-pid)`），确保无残留子进程；`timeout` 参数改为显式 kill 逻辑。

### 验收
1. SSH：构造 listen 失败的场景（如端口被占），断言 server 句柄释放、close 不挂起。
2. MCP：超时场景（git 命令挂死）断言子进程被 kill、无残留；typecheck 全绿。
