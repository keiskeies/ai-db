# 性能与挂起隐患修复计划（2026-11-17 全面性能排查产出）

本文档是性能排查（长时间执行 / 长时间无响应 / 长时间响应）的落地修复计划。所有 `file:line` 为排查时点锚点，**修改前请重新确认**。

修复按 5 个工作包（WP1–WP5）并行落地，**每个工作包独占一组文件，禁止越界修改**；跨包接口以「契约」小节为准。

## WP1 驱动层真超时与结果上限（独占 `apps/gateway/src/drivers/*.ts`）

### D1 MySQL（高）
锚点：`drivers/mysql.ts:106`（`query({ sql, values, timeout })`）、`:186-187`（池配置）。
- mysql2 的 `query()` **不支持 timeout 选项**，删除该无效传参。
- 真超时方案（组合）：
  1. 仅对 SELECT（含 WITH…SELECT）注入优化器提示 `/*+ MAX_EXECUTION_TIME(ms) */`，覆盖事务内 SELECT；
  2. 客户端看门狗：`setTimeout(timeoutMs)` 到期后 reject（错误码沿用现有超时语义，如 `QUERY_TIMEOUT`），**非事务**时 `connection.destroy()`（服务端查询随连接终止）；事务内不销毁连接（沿用现有注释约束），DML 锁等待依赖会话级 `innodb_lock_wait_timeout`（连接建立时 SET 为合理值，如 30s，可被 opts 覆盖）；
  3. 看门狗与流式截断路径（现有 settle/truncated 逻辑）正确协同，定时器必须在 settle 时清理，防止泄漏与重复 settle。
- 池获取排队超时：`getConnection` 包一层超时（默认 10s，超时 reject `POOL_TIMEOUT`）。注意竞态：超时后若连接迟到，必须 `release()` 归还，不得泄漏。池 `connectionLimit` 保持现状或提到 5（说明理由）。

### D2 PostgreSQL（高）
锚点：`drivers/postgres.ts:288-303`。
- 服务端真超时：执行前 `SET statement_timeout = <ms>`，结束后 `RESET statement_timeout`（同一 acquired client 上，finally 保证 reset；reset 失败则销毁该 client 不回池）。超时错误映射为现有超时错误码。保留现有客户端计时作为兜底，但到期且非事务时销毁 client（真正终止服务端查询）。
- 内存：无 pg-query-stream 依赖（**不许加依赖**）。对单条 SELECT/WITH 语句下推 `LIMIT maxRows+1` 外包（`SELECT * FROM ( … ) AS _aidb_limit LIMIT n`，与 Oracle 现有做法对齐；多语句/非 SELECT 不包），截断时置 truncated。无法下推的路径在注释中说明残留风险。

### D3 SQLite（高）
锚点：`drivers/sqlite.ts:94,140`。
- node:sqlite 同步 API 无法真正异步化。优先检查运行时 `StatementSync.prototype.iterate` 是否可用（Node ≥22.13 按 engines 约束）：可用则用 `iterate()` 逐行读 + 行数/字节双上限（对齐 mysql.ts 的 64MB 常量语义），到达上限提前 break；不可用则对单条 SELECT/WITH 下推 `LIMIT maxRows+1`，读入后按字节上限裁剪并置 truncated。
- describe 的每表 `COUNT(*)`：改为不精确行数（`sqlite_stat1` 可用时读取，否则省略行数字段或置 undefined），禁止全表扫描。
- 同步阻塞本身无法消除，在代码注释中说明；上限保证最坏情况有界。

### D4 DuckDB（高）
锚点：`drivers/duckdb.ts:107-109`。
- 检查 `@duckdb/node-api` 已安装版本的流式 API（`connection.run` 返回的 reader 是否支持分块读取，如 `readChunk`/逐行）：支持则流式 + 行数/字节双上限 + truncated；不支持则单条 SELECT 下推 `LIMIT maxRows+1`。
- 超时：看门狗到期调用 DuckDB 的 `interrupt()`（若 API 存在）并 reject；连接按现有生命周期管理。

### D5 MongoDB（中）
锚点：`drivers/mongodb.ts:247-252,301-315`。
- MongoClient 选项补 `socketTimeoutMS`（如 60s，保留现有 connectTimeoutMS）。
- `listCollections`、`estimatedDocumentCount`、采样 find/aggregate 全部补 `maxTimeMS`（与现有查询路径一致的超时值）。

### D6 内省超时（中）
锚点：`mysql.ts:234-262`、`postgres.ts:108-167`、`oracle.ts:139+`。
- information_schema / catalog 内省查询统一传超时（默认 30s，走各驱动已实现的超时机制）。Oracle describe/connection 补 `callTimeout`。

### WP1 验收
- `npm --workspace @aidb/gateway run typecheck` + gateway 单测。
- 有真实引擎的回归脚本（docs/10 提到的 MySQL 回归）如可运行则跑；不可运行则说明。
- 新增/调整单测覆盖：MySQL 看门狗超时 destroy、PG statement_timeout 设置与 reset、LIMIT 下推判定（SELECT/WITH/多语句/非 SELECT）。

## WP2 网关请求生命周期（独占 `routes.ts`、`executor.ts`、`manager.ts`、`scheduler.ts`、`search.ts`、`server.ts`、`index.ts`，均在 apps/gateway/src）

### G1 查询取消（高）
锚点：`routes.ts:510-556`（POST /query）、manager 查询执行路径。
- POST /query 监听 `req.on('close')`（请求提前断开）：若查询仍在执行且**不在事务中**，销毁该查询占用的驱动连接（MySQL/PG 连接断开即终止服务端查询；其他引擎按驱动能力尽力而为）。manager 需暴露「按执行追踪活动连接/取消句柄」的内部机制（实现方式自定，保持对外 API 兼容）。
- 事务内查询不销毁连接（沿用驱动层约束），仅标记放弃结果。
- 客户端主动取消：前端 F2 通过 abort fetch 触发同一 close 路径，无需新端点。

### G2 超时漏传（中）
锚点：`routes.ts:2119`（/export）、`executor.ts:835,854,1616,1647`（画像/COUNT DISTINCT 质检）、`manager.ts:1319`（execScript）。
- 全部补 timeoutMs：普通查询路径用现有默认（30s）；导出用 120s；execScript（备份恢复整段脚本）用 600s；质检 COUNT DISTINCT 用 120s。常量集中定义，注明理由。

### G3 search body 超时（高）
锚点：`search.ts:125-137`。
- 现状：fetch resolve（收到响应头）即 finally clearTimeout，之后 `response.text()` 裸等。
- 改为单个 `AbortSignal.timeout(timeoutMs)` 覆盖「请求 + body 读取」全程，body 读完才结束计时；超时错误沿用 `SEARCH_TIMEOUT`。

### G4 scheduler 任务级超时（中）
锚点：`scheduler.ts:51,66-73,90,190`。
- artifact/dashboard runner 与备份 dump 包任务级超时（默认 600s）；`waitForRun` 传入超时（契约 K2），超时后释放 running 槽并记录失败，杜绝永久停摆。

### G5 SSE/WS 背压与死连接（中）
锚点：`routes.ts:2527,2876,3120`、`server.ts:172-177,228-239`。
- SSE：检查 `res.write()` 返回值，持续 false 且积压超阈值（如 1MB）时断开慢客户端（close 清理沿用现有逻辑）。
- WS：send 前查 `bufferedAmount`（>1MB 丢弃该客户端）；ping 后记录时间，超过 90s 无 pong（或无任何入站消息）则 terminate。
- **契约 K3**：schema WS 增加应用层心跳——收到客户端 `{type:'ping'}` 回 `{type:'pong'}`（浏览器 JS 看不到协议层 ping，必须应用层）。

### G6 executor 配套（中）
锚点：`executor.ts:1272-1295`（skill 轮询）、`executor.ts:1349-1360`（MCP 调用）。
- skill 轮询加总时长上限（与 skillRunner 的 10min 默认对齐，超时按失败处理）。
- MCP 调用传 `ctx.signal`（契约 K1：WP3 给 mcp client.call 增加可选 signal 参数；两边独立可编译）。

### G7 HTTP server 超时（低）
锚点：`index.ts:16` 附近。显式设置 `requestTimeout`（120s）、`headersTimeout`（60s）、`keepAliveTimeout`（10s）。注意：SSE 长连接不受 requestTimeout 影响需验证（Node requestTimeout 针对请求接收阶段，确认不误伤 SSE；如有误伤风险改用 headersTimeout + keepAliveTimeout 并说明）。

### E6 配套：inline 导出改流式（高，与 WP5 契约 K4）
锚点：`routes.ts:2125`（`readFileSync(file.path).toString('base64')`）。
- WP5 将 `writeExportFile` 改为异步文件生成（不再返回大 Buffer）。inline 分支改为：响应直接流式输出文件内容（`res.sendFile`/createStream，content-type 按格式，附下载文件名），或提供 `GET /export/file?path=` 下载端点（路径必须校验在 exportDir 内，防目录穿越）。前端契约 K5：WP4 适配 inline 响应形态。**选择其一并在此记录决定**（推荐：新增下载端点 + 响应返回下载 URL，JSON 响应不再含 base64）。
- **WP2 决定（已落地）**：采用推荐方案——新增 `GET /api/export/file?path=`（Bearer 鉴权 + exportDir 内 resolve 校验防穿越 + res.download），`/export` 与 `/artifacts/:id/export` 的 inline 分支返回 `downloadUrl` 字段，不再含 base64；`file` 元数据保持兼容。详见契约汇总 K5 行。

### WP2 验收
gateway typecheck + 单测；新增单测覆盖 req close 取消、search body 超时、scheduler 超时释放槽。

## WP3 core 提供商/流水线 + worker/MCP（独占 `packages/core/src/agent/**`、`packages/core/src/pipeline/http.ts`、`packages/core/src/pipeline/script.ts`、apps/gateway/src 的 `skillWorker.ts`、`skillRunner.ts`、`mcp.ts`、`builtinMcp.ts`、`commands/runner.ts`，可新建共享小工具文件）

### C1 Ollama 绝对上限（高）
锚点：`packages/core/src/agent/providers/index.ts:31`、`providers/common.ts:28,51,86,121`。
- 保留 stallMs:0 的设计意图（本地 prefill 数分钟不吐字节不是卡死，注释已说明），但增加**绝对截止时间**：默认 15min，环境变量 `AIDB_PROVIDER_DEADLINE_MS` 可覆盖；到期 abort 并给出明确错误（区别于停摆错误）。连接建立阶段另设较短超时（如 30s）。
- 其他提供商的停摆看门狗保持不变。

### C2 pipeline/http body 超时（高）
锚点：`packages/core/src/pipeline/http.ts:97,107`。
- 与 G3 同模式：单个 AbortSignal.timeout 覆盖请求+body 全程，reader.read() 期间保持计时。

### C3 杀进程树（中）
锚点：`skillRunner.ts:243,249`、`mcp.ts:45,156`、`pipeline/script.ts:125`、`builtinMcp.ts:553`（已有 killTree）。
- gateway：把 builtinMcp 的 killTree 提取到共享模块（如 `apps/gateway/src/processTree.ts`），skillRunner、mcp close 复用；Windows `shell:true` 场景用 `taskkill /pid <pid> /T /F`。
- core/pipeline/script.ts：core 不能 import gateway 模块，自带一份等价实现（Windows taskkill /T；POSIX spawn 时 detached + kill(-pid) 进程组）。

### C4 skillWorker 治理（中）
锚点：`skillWorker.ts:83,118,180,185-192`。
- workers Map：worker 结束即 delete；另加周期清扫（如每 5min 清理结束超过 10min 的条目）。
- REST 启动的 worker 加整体超时（默认 30min，与 skillRunner 上限对齐）。
- `skill_ask` 等待加超时（默认 5min，与审批自动拒一致），超时按拒绝/失败返回。

### C5 MCP 信号与回收（中）
锚点：`mcp.ts:113,137,162`。
- **契约 K1**：`call(tool, args, opts?: { signal?: AbortSignal; timeoutMs?: number })`（可选参数，旧调用不受影响）；signal abort 时 reject 并尽力终止底层请求；默认超时保持 20s，长任务可由调用方传更大 timeoutMs。
- 常驻客户端缓存加空闲回收（如 10min 未使用则 close，复用 killTree）。

### C6 runner 治理（中）
锚点：`commands/runner.ts:84,160,189-196,637`。

- **契约 K2**：`waitForRun(runId, timeoutMs?: number)` 可选超时参数，超时 resolve undefined（或 reject，与 scheduler 现有错误处理对齐，二选一并记录）。

### C7 LLM 重试退避（低）
锚点：`packages/core/src/agent/runtime.ts:664-670`。

## WP4 前端请求与渲染（独占 `apps/desktop/src/**`）

### F1 request 超时（高）
锚点：`lib/api.ts:94-120`。
- `request()` 默认 `AbortSignal.timeout(30_000)`；支持调用方传 `signal` 与超时覆盖（schema 60s、导出/导入 300s、备份恢复 600s）。与调用方 signal 组合（任一 abort 即中止）。
- 超时错误转成现有 ApiError 形态 + i18n 文案（走现有 tr() 与 i18n 流程，新增文案需同步 extract）。

### F2 查询取消入口（高）
锚点：`QueryView.tsx:661`（运行按钮）、`:417-445`（runScript）。
- 执行中运行按钮变为「取消」：abort 当前 fetch（后端 G1 close 路径终止查询）；runScript 同样支持。UI 状态与现有 runSeq 守卫协同。

### F3 本地 abort（高）
锚点：`store.ts:1338-1346`（abortAgent）。
- 先调 `currentAbort.abort()` 立即断流，再 POST /abort（失败静默，本地已断）。

### F4 SSE idle 检测（高）
锚点：`api.ts:342-372`（readSse）、`:450`（streamCommandRun）、`:491`（streamSkillRun）。
- 复用 streamTurn 已有的 idle 看门狗模式（字节/事件双层），抽成共享小工具；idle 上限按流类型设置（command/skill 执行期间可能长时间无输出——用字节层 idle 而非事件层，阈值放宽到 120s 并说明）。

### F5 AI 流式渲染（高）
锚点：`store.ts:1092-1114`、`AgentPanel.tsx:1260,1840`、`ui.tsx:478`、`MarkdownBody.tsx:21`。
- 历史消息组件 React.memo（按消息对象引用/稳定 key），流式期间只有 live 消息重渲染。
- live 文本 delta 节流合并：rAF 或 50ms 定时 flush 到 store，避免每 token 一次全量 set；tools/plan/timeline 不变时不复制。
- MarkdownBody 对静态消息不重解析（memo 生效后自然达成）；live 消息保持每 flush 解析一次。

### F6 竞态与导出反馈（中）
锚点：`DataView.tsx:152-177,557-563`、`QueryView.tsx:492-501`。
- DataView load 加 seq 守卫（对齐 QueryView runSeq 模式）；导出加 loading 态 + 取消按钮（abort fetch）。

### F7 大单元格渲染（中）
锚点：`lib/format.ts:9`、`DataGrid.tsx:206-213`。
- 对象单元格预览截断（如 2KB），title 同样截断（如 1KB）；完整值查看走现有单元格详情交互（若有）。

### F8 杂项（低）
- `api.ts:518-528` objectURL 缓存加上限（如 100 条 LRU）+ revoke 淘汰项。
- `QueryView.tsx:378-415` keydown effect 补依赖数组。
